---
name: pitch
description: Pitch a non-trivial code change once the problem and desired behavior are sufficiently aligned, after inspecting the current code and before implementation. Restate the task, show the current-to-proposed call flow as a colored diff tree, justify every structural change, define the data contracts and scope, and wait for go-ahead. Also use when the user says "pitch", "don't code yet", or "say it back".
---

Do not pitch during early discovery or while material requirements remain
unresolved. Enough alignment exists when the desired behavior and material
contracts are settled enough to name the concrete code path and scope. Ask one
question at a time until then.

Once aligned, read the current code and deliver the pitch before implementation.
Don't pitch against a stale mental model. If the codebase contradicts an
assumption in the task, surface it in the pitch. Do not write or edit code until
I give the go-ahead. The pitch is the deliverable.

Pitch the change in this shape, keeping the whole thing short and scannable:

1. **Task, said back.** One line restating what I asked for. If your restatement adds, drops, or reinterprets anything, stop and ask instead.

2. **Call-flow diff.** Show the current and proposed code paths together as one or more Calldiff-style trees in fenced `diff` blocks. Use unprefixed lines for unchanged context, `-` for calls or branches being removed, and `+` for calls or branches being added so renderers color the flow. Start at the real request, event, command, or public function entrypoint and expand through named functions, boundaries, persistence, and external systems to the result. Split independent entrypoints into separate trees. For example:

   ```diff
   POST /widgets
     └─ createWidget()
        ├─ validateInput()
   -    ├─ writeLegacyWidget()
   +    ├─ widgetRepository.insert()
   +    └─ publishWidgetCreated()
   ```

   Manually render the proposed diff when code does not exist yet; do not claim it was generated by `calldiff`. Prefer behavioral calls and ownership boundaries over incidental query-builder methods. The tree replaces separate prose walkthroughs of the current path and proposed call graph, but add one short note for an important invariant the tree cannot express.

3. **Contract diff.** When types, fields, states, events, or boundary payloads change, show their current-to-proposed shape in another fenced `diff` block. Include validation and transformations at the boundary where they occur. Omit this section only when no meaningful contract changes.

4. **Proposed changes, each justified.** List every file, type, field, data structure, function, parameter, and abstraction to add, update, move, or delete. Explain why each change is necessary and identify the canonical existing pieces to reuse. Anything that cannot be justified in one line does not get written. Name every new export as a search address: two to four words, at least one domain word, unique under grep, reusing the codebase's one established noun for each concept. A name that repeats module context, encodes the lookup key, or runs past four words gets fixed here, not in review.

   Every new public API field must name a current consumer or required workflow and explain why that data belongs at the public boundary. Internal derivability, symmetry, completeness, or possible future use is not sufficient. If no current consumer or workflow requires the field, omit it from the pitch.

5. **Scope and structure.** Show a compact proposed file tree rooted at the closest shared domain. Mark files to add, update, move, or delete, and justify each placement by ownership and responsibility. Keep domain behavior with its owning domain instead of dropping it into generic grab-bag directories or modules. Name every file you'll touch and nothing else. If the change wants to spill into unrelated code, say so here instead of doing it.

   Every new file must establish a distinct responsibility and explain why the nearest existing owning module is not the correct home. A few small helpers, a second caller, or a desire to avoid imports does not by itself justify another file. If the responsibility already has a canonical owner, extend that module instead.

Treat the pitch as a living implementation model. When I ask to revisit the plan, or code discovery changes an assumption, update the affected code paths, types, abstractions, data flow, file structure, and call graph.

After the go-ahead, implement exactly the pitch. If implementation forces a deviation, stop and say what changed and why before continuing.
